# Сверка старых покупок

Метка `migration_catalog_unverified` означает, что старая БД не сохранила условия покупки. Текущий тариф не является доказательством прежних условий. Для сверки нужны чек или подтверждённый архив заказа и журнал выдачи доступа.

Команда доступна главному администратору из настроенного `ADMIN_IDS`. Не меняйте права ради обхода проверки. Сначала испытайте процедуру на отдельной копии БД и сделайте backup. Команда использует обычный `DATABASE_URL` приложения; проверьте выбранную БД перед запуском. Данные чеков, токены и персональные сведения в аргумент `--reference` не вставляйте: достаточно ссылки на внутреннюю запись.

## Невыданная покупка

Убедитесь по журналу, что платёж ранее не выдавал доступ. Уточните срок и канал по документам покупки. Сначала выполните просмотр без записи:

```sh
python -m app.scripts.reconcile_purchase --actor 42 --payment 123 --channel 7 --days 30 --reference "archive-order-123"
```

Проверьте идентификатор, провайдера, сумму, валюту, прежние непроверенные значения и предложенные условия. Значения в примере замените на проверенные данные. При подтверждении повторите команду с `--apply --confirm-unapplied`:

```sh
python -m app.scripts.reconcile_purchase --actor 42 --payment 123 --channel 7 --days 30 --reference "archive-order-123" --apply --confirm-unapplied
```

Условия сохраняются вместе с AuditLog. Для уже оплаченной покупки в той же транзакции создаётся или возобновляется задача выдачи. Команда не обращается к Telegram и провайдерам, не изменяет сумму, валюту и статус оплаты. После сохранения проверенные условия повторно изменить этой командой нельзя.

Без `--apply` команда ничего не записывает. Без явного подтверждения отсутствия прежней выдачи применение запрещено. При ошибке подключения проверьте AuditLog перед повтором: ошибка ответа не доказывает, что commit не состоялся.

## Покупка с историческим доступом

При наличии PaymentApplication или привязки к Subscription команда откажет в довыдаче. Она не снимает legacy-маркер, не угадывает прежние периоды и не меняет вручную добавленные дни. Для таких записей сначала восстановите фактические периоды по журналам и согласуйте итоговое состояние доступа. Автоматизированная сверка всей утраченной истории периодов пока не поддерживается.

Не удаляйте legacy-записи ради повторной выдачи и не меняйте payment_id наугад. Возврат через интерфейс блокируется до подтверждения истории; внешнее завершение возврата и его влияние на доступ требуют отдельной сверки. Сохраните подтверждённые факты и решение оператора в журнале.
