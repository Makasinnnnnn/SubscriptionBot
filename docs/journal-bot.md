# Telegram-бот журнала сделок

Отдельный бот для существующего Google Sheets-журнала. Модуль: `app/journal`.
Он не импортирует конфигурацию подписочного бота и не меняет платежи, подписки,
существующие миграции или production-сервисы PropGate.

## Что реализовано

- Кнопки открытия и закрытия сделок, карточки, поиск по ID и списки с пагинацией.
- Пошаговый ввод, возврат, отмена, подтверждение, восстановление черновика после перезапуска.
- Ввод количества монет или расчёт по проценту риска с подтверждением.
- Long/Short, необязательный стоп, комиссии/финансирование, фактический чистый PnL, включая 0.
- Несколько скринов и Telegram-альбомы; фотографии или JPG/PNG/WebP-документы.
- Хранение оригиналов в закрытой папке Google Drive и ссылок на вкладке Скриншоты.
- Allowlist Telegram ID, доступ трейдера к заданным счетам, администратор для чужих сделок.
- Транзакционная выдача свободных TR-ID, долговечная очередь, повторы и журнал изменений.
- Поиск строки по ID перед обновлением; формулы и оформление не перезаписываются.
- Обнаружение ручных правок и отдельное подтверждение их замены данными бота.
- Отдельные миграции с таблицами `journal_*` и версией `journal_alembic_version`.

## Что нужно для реального запуска

1. Отдельный токен Telegram-бота от BotFather.
2. Telegram user ID администратора и трейдеров; email для авторизации Telegram не подходит.
3. Runtime-авторизация Google с правом редактировать таблицу и загружать файлы в папку.

MCP Google Drive, которым создавали таблицу, не является авторизацией запущенного бота.
25.10.2026 подключена пользовательская OAuth-авторизация, проверена актуальная схема
рабочей таблицы и доступ на загрузку в папку скриншотов. Перед новым развёртыванием
обязателен `app.journal.check`.

## Установка

Все команды выполняются из корня репозитория, содержащего `pyproject.toml`:

```powershell
cd C:\Users\MaXiM\Documents\GitHub\SubscriptionBot\SubscriptionBot
uv pip install --python .venv\Scripts\python.exe -r requirements-journal.txt
Copy-Item config\journal.example.txt .env.journal
```

Если отдельного окружения ещё нет: `uv venv .venv`, затем команда установки выше.
Также подходит обычное `python -m venv .venv` и `python -m pip install -r requirements-journal.txt`.
Версия Python: 3.11 или новее. Тестовые инструменты: pytest, pytest-asyncio, ruff.

Пример конфигурации без реальных секретов: `config/journal.example.txt`.
В проекте `.env*` исключены из Git; рабочий `.env.journal` не коммитится.

Обязательно заполнить:

```dotenv
JOURNAL_BOT_TOKEN=получить_у_BotFather
JOURNAL_ADMIN_IDS=[111111111]
JOURNAL_TRADER_ACCOUNTS={"222222222":["1"]}
JOURNAL_DATABASE_URL=sqlite+aiosqlite:///journal.db
```

Администратор видит все импортированные счета и может исправлять чужие сделки.
Трейдер видит разрешённые счета и может изменять только собственные сделки.
Неизвестный пользователь получает свой Telegram ID и отказ в доступе.

Для PostgreSQL укажите свой URL `postgresql+asyncpg://USER:PASSWORD@HOST:5432/DATABASE`.
Можно использовать сервер PostgreSQL PropGate с теми же библиотеками: журнал создаёт
только свои таблицы. Сначала проверьте миграцию на копии БД и сохраните backup.

## Google: рекомендуемый путь для личного My Drive

Используйте OAuth пользователя, которому принадлежат таблица и папка. Это решает
ограничение service account: он обычно не может владеть новыми файлами в личном
My Drive из-за отсутствия собственной квоты хранилища.

1. В Google Cloud создайте/выберите проект, включите Google Sheets API и Google Drive API.
2. Настройте OAuth consent screen. Для тестового режима добавьте свой Google-аккаунт
   в test users; проверьте срок действия refresh token в выбранном режиме проекта.
3. Создайте OAuth Client ID типа Desktop app, скачайте JSON.
4. Сохраните JSON вне репозитория по пути
   `C:\Users\MaXiM\.config\propgate-journal\client.json` либо задайте
   `JOURNAL_GOOGLE_CLIENT_SECRET`.
5. Выполните:

```powershell
.venv\Scripts\python.exe -m app.journal.authorize
```

Откроется браузер для вашего входа и согласия. Refresh token сохраняется вне
репозитория в `~/.config/propgate-journal/google.json`, не выводится в терминал.
При существующем файле команда не перезаписывает его. На Windows проверьте ACL
папки: доступ нужен только пользователю, запускающему бота.

Запрашиваются Sheets и Drive scopes; доступ OAuth соответствует правам выбранного
Google-аккаунта. Для минимизации доступа можно выделить отдельный аккаунт и открыть
ему только журнал/папку. Сам бот права Drive не меняет и публичные ссылки не включает.

Service account также поддерживается через `JOURNAL_GOOGLE_CREDENTIALS`:
для редактирования Sheets нужны права на таблицу, а для загрузки скринов — подходящий
Shared Drive с правами создания файлов. Просто поделиться папкой личного My Drive
с service account может быть недостаточно. Для данного личного проекта выбирайте OAuth.

## Проверка и запуск

```powershell
.venv\Scripts\python.exe -m app.journal.migrate
.venv\Scripts\python.exe -m app.journal.check
.venv\Scripts\python.exe -m app.journal
```

Миграция не запускает подписочные миграции. Её повторное выполнение безопасно.
`check` делает только чтение: проверяет часовой пояс, вкладки, заголовки,
покрытие нативных таблиц, 300 уникальных ID и наличие формульных ячеек.
Она не доказывает математическую корректность пользовательских формул.

При первом запуске без Google-авторизации или при несовпадении схемы бот не начинает
приём данных. При кратком сетевом сбое после успешного запуска данные сохраняются
в БД. После перезапуска во время краткого сбоя можно продолжать по ранее проверенному
кэшу счетов; каждая запись в Google всё равно требует свежей успешной проверки схемы.

Запускайте один polling-процесс на один Telegram-токен. Очередь встроена в этот процесс.
Корректность транзакций обеспечивается блокировкой в БД, а не только asyncio-lock.

## Docker

Отдельный Compose не затрагивает существующие сервисы:

```powershell
$env:JOURNAL_GOOGLE_SECRET_FILE='C:\Users\MaXiM\.config\propgate-journal\google.json'
docker compose -f docker-compose.journal.yml up --build -d
docker compose -f docker-compose.journal.yml logs -f journal
```

Этот Compose использует SQLite в отдельном volume `journal_data`, контейнер работает
без root. Для PostgreSQL замените JOURNAL_DATABASE_URL у обоих journal-сервисов;
не меняйте URL только у одного. Credentials передаются через Docker secret read-only
и не копируются в образ. Файл должен быть читаем пользователем контейнера.
OAuth первично выполняется локально, полученный credential-файл монтируется на сервере.

## Первая сделка

1. `/start` → Открыть сделку → заполнить поля.
2. Счёт проп1, ID 1, начальный баланс $200 000 импортируется из Google Sheets.
3. Баланс перед входом требуется подтвердить: исходная сумма не подменяет баланс платформы.
4. До «Сохранить» это только черновик. После — постоянный TR-ID и операция очереди.
5. При закрытии используйте ту же карточку, время, цену и способ расчёта результата.
6. Скрины можно отправлять на шаге изображений или отдельно через меню.

Google Sheets: https://docs.google.com/spreadsheets/d/1hTq6mZUNivnEsxMi5B4hjDuDhoh7WcQVJ3JRqkiChE8/edit

Фото сохраняются как отдельные записи с тем же TR-ID. Колонка E изображения остаётся
свободной: обычный Sheets API надёжно заполняет приватную ссылку Drive в D, а не
создаёт нативное приватное изображение в ячейке. Вставить картинку можно вручную.

## Конфликты и ограничения

- После ручного редактирования входных полей автоматическая замена блокируется.
  В меню Статус → Конфликт можно просмотреть значения и явно подтвердить замену
  данными бота. Для сохранения ручных данных отмените замену и исправьте карточку бота.
  Полной двусторонней синхронизации нет.
- Sheets API не предоставляет атомарный compare-and-swap для ячеек. Проверка перед
  записью и readback обнаруживают обычные конфликты, но не могут гарантировать защиту
  от ручной правки в точном промежутке между проверкой и записью. Не редактируйте и не
  сортируйте одну позицию одновременно с её синхронизацией; бот сообщает обнаруженные конфликты.
- Расчёты — для линейных контрактов в USD/USDT. Не учтены инверсные контракты и
  динамическая маржа. Для сложных выходов используйте средневзвешенные цены и факт PnL.
- Риск бота — до стопа, без комиссий и проскальзывания. В исходном шаблоне Sheets
  стоп на уровне входа/с прибыльной стороны может показывать «Проверь стоп», тогда
  как бот считает нулевой ценовой убыток. Бот не меняет эти пользовательские формулы.
- Лимит: 300 сделок и 300 скринов. При заполнении запись останавливается с объяснением;
  автоматического расширения формул нет. Для каждой новой сделки ID закрепляется в БД.
- Очередь и мастера сериализованы одной блокировкой БД. Во время Google-запроса ввод
  может кратко ожидать; это решение для небольшой команды, не для массового сервиса.
- До 20 изображений на подтверждение; файл до 15 МБ. Оригинал временно хранится
  в БД и очищается оттуда после успешной записи Drive + Sheets. Telegram file_id и
  приватная ссылка сохраняются. Учтите это при настройке резервных копий и хранения.
- Общий результат — только реализованный PnL, без выводов, пополнений, открытого
  результата и доли проп-фирмы. Расчётный баланс не является доступной выплатой.

## Проверки разработки

```powershell
.venv\Scripts\python.exe -m pytest -c journal_tests/pytest.ini journal_tests -q
.venv\Scripts\python.exe -m ruff check app/journal journal_tests
```

Тесты отделены от `tests/conftest.py` подписочного проекта. Используют временную БД,
заглушки Telegram/Google и HTTP MockTransport. В рабочую таблицу тестовые сделки не пишутся.
Проверяются расчёты, мастера, ID-конкурентность, повторы, возобновление, скрины,
конфликты, сортировка, поля записи и самостоятельная миграция.

25.10.2026: 38 тестов прошли, Ruff — без ошибок. Подключены OAuth и реальный polling
Telegram для @proptablebot; проверены чтение Sheets и право добавлять файлы в папку Drive.
Сквозная запись сделки и upload скрина проверяются первой реальной подтверждённой сделкой:
фиктивные записи в рабочую таблицу не вносились. PostgreSQL и Docker требуют отдельной
приёмки в вашем окружении; локальная автоматическая проверка использует SQLite.
